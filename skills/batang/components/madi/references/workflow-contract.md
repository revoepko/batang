# 마디 실행 계약

이 계약은 명시적으로 선택한 개발·문서·도면 작업의 기본값이다. 사용자 지시와 프로젝트 고유 계약이 우선한다. 이 패키지는 실행기나 진행 상태 API가 아니라 작업·근거 기록 방식이다.

## 경계와 시작

실제 적용되는 사용자·프로젝트 정책, 승인 범위, 기존 profile/run과 실제 호스트 규약을 먼저 읽는다. 기존 API 기반 run, 현재 설치, 운영 vault와 기존 pin은 자동 변환하거나 수정하지 않는다.

새 run은 한 고정 checkout revision의 Batang skill과 `components/madi/workflow.md` 경로를 고정한다. 진행 중 run이 사용하는 실제 파일은 해당 경로와 hash가 고정된 동안 수정·갱신하지 않는다. 갱신은 기존 checkout을 당겨 바꾸는 대신 새 checkout 또는 새 고정 디렉터리를 준비하고 새 run에서 선택한다.

Checkout root `SHA256SUMS`는 파일별 SHA-256 목록이다. 목록에 적힌 모든 파일과 `SHA256SUMS` 파일 자체의 SHA-256에 대한 유효한 근거를 확인하고 bundle identity를 run에 기록한다. 동일 고정본의 유효한 근거는 실행 간 재사용한다. 새 등록 선택·설치·전송이나 관련 변경·오류·불명 시 다시 대조한다.

로컬 release의 `candidate-manifest.json` 및 archive hash는 별도 후보 근거로 유지하며 이 bundle identity로 대체하지 않는다. Profile hash는 profile을 실제 저장한 뒤 해당 bytes로 계산해 run 기록에만 쓴다.

선택한 자료와 요청된 작업에 필요한 도구의 접근을 준비한다. Markdown 직접 조회에는 Graphify와 Archify가 필요하지 않다. 호스트는 Markdown을 직접 다루며 Obsidian 앱을 자동으로 열거나 등록하지 않는다.

Graphify는 관계 작업과 승인된 갱신에, Archify는 요청된 설명·도면에 사용한다.

지식 자료 작업에서 필요한 vault·활성 목록이 없거나 충돌하면 필요한 값을 묻고 승인 전 쓰기 0건으로 둔다. 독립 코드·문서 작업에 운영 vault를 선행 조건으로 삼지 않는다. 준비된 Graphify의 실패는 Markdown 원본의 유효성과 분리하고 이전 graph를 보존한다. 누락·접근 불가·권한 부재는 해당 단계 `BLOCKED`이며 자동 설치·경로 탐색·provider 전환은 하지 않는다.

준비 확인은 [가닥](../../gadak/workflow.md)의 유효 근거 재사용 조건을 따른다.

## 계획·검토·검증

요구마다 담당, 소유 파일 또는 모듈 경계, 의존성, 관찰 가능한 acceptance, 검증 방법·환경·예상 결과를 연결한다. 사용자 결정·위임·가정·미정을 구분하고 범위·권한·provider·검증 깊이를 넓힐 때만 사용자에게 질문한다.

메인은 요청·권한과 작업의 독립성·의존성을 보고 직접 처리 또는 위임의 필요성을 판단하며 결과를 확인한다. 역할 책임은 실제 호스트에서 이용 가능한 역할에 매핑한다.

위임할 때 목표, 적용 정책·절차, 자료·권한과 범위, 소유 파일, 의존 관계, 완료 조건과 필요한 증거를 전달하고 호스트에서 관찰 가능한 역할·문서 참조·행동·결과를 확인한다. 내부 전달문 수신이나 바이트 증명, 특정 ACK를 강제하지 않는다. 관찰할 수 없는 사항은 미확인으로 남기고 실제 계약 실패와 구분한다.

요청한 역할·모델과 실제 호출을 구분하고 차이나 대체 이유를 기록한다. 위임 주체·깊이·슬롯·도구는 적용되는 지침 우선순위와 호스트 권한 한도를 따른다. 자식도 수신한 범위와 실제 재위임 규약을 따른다. 특정 모델 자동 호출이나 provider 추가·자동 fallback은 제공하지 않는다.

시험의 합격·실패·차단 조건, 필수 환경·횟수 또는 정확한 출력 조건을 기존 승인 기준에 없게 추가하거나 기존 조건을 실질적으로 변경하면 적용 전에 이유와 영향을 사용자에게 질문하고 명시 승인받아 기존 계획 또는 시험 조건 목록에 내용·근거·범위를 등록한다. 승인 전에는 해당 조건을 판정에 적용하지 않는다. 기존 승인 조건의 구현 확인과 비차단 진단에는 반복해 묻지 않는다. 비차단 관측을 필수 판정 조건으로 승격하면 승인·등록한다. 별도 승인 API·의무 템플릿·서명·ACK를 추가하지 않는다.

검토의 필요성·종류·순서·횟수 및 릴리즈 조건은 사용자와 프로젝트의 적용 규약을 따른다. 단순 작업은 적용 규약에 따라 직접 처리할 수 있으며 선택 양식의 모든 필드나 planner·writer·reviewer 호출을 일률적으로 강제하지 않는다. 검증 방법은 변경 영향과 근거에 맞게 선택한다. 기존 역할·모델·추론 수준을 존중하며 프로필명과 책임을 구분한다. 필수 모델·모드 또는 검토를 수행하거나 확인하지 못하면 해당 단계는 `BLOCKED`다. 필수 조건을 임의 완화하지 않는다. 독립 검토가 요구되거나 수행되면 작성자와의 독립성, 고정 대상·범위·호출·결과와 실패 이력을 실제 근거로 보존한다.

문서 전용 분기에서는 계획 담당이 reviewer·품질 검토·보안 검토의 필요성, 범위와 제외 이유를 판단해 기록한다. 적용되는 일반 작성자 검토와 프로젝트 필수 검토를 완화하지 않는다. 독립 검토에는 고정된 대상을 제공하고 작성자와 검토자를 분리한다.

요구와 승인 범위, 완료 단계, 실패·부분 성공, 남은 단계 및 각 관찰 근거를 기존 기록에 연결하고 후속 담당에게 필요한 재개 조건을 전달한다. 재개 판단은 [두레](../../dure/workflow.md)를 따른다. 설명 변경은 문서 검토로 확인하고 동작·재개·권한에 관한 주장은 필요한 합성 실행 또는 실제 환경 관측으로 확인하며 그 범위와 미실행을 구분한다. 개발에 사용하는 고정본과 평가 후보를 분리하고 사용자 요구와 관찰 가능한 결과로 평가한다. A/B 비교는 선택 사항이다.

기존 정책 파일과 계획·기록 방식을 사용하고 필요한 경우 참고 양식을 선택한다. 중복 프로필·전역 모델 설정이나 자동 저장을 강제하지 않는다. 실제 결과·미확인·근거 유효성과 기존 이력은 보존한다.

`PLAN_READY`는 계획 착수 기준, `TASK_DONE`은 승인 범위의 산출물·필수 검토·검증이 충족한 기록, `RELEASE_READY`는 릴리즈 게이트 충족 기록이다. 모두 호스트가 실제 Markdown 근거와 관찰을 해석해 판단한다. 이 패키지는 자동 기계 검사·상태 전이·완료 제출을 제공하지 않는다.

| 축 | 값 |
|---|---|
| 단계 | `planning` / `implementation` / `review` / `verification` / `release` |
| 작업 상태 | `pending` / `active` / `paused` / `blocked` / `done` |
| 검토 판정 | `approve` / `request_changes` / `blocked` / 공란 |
| 검증 결과 | `PASS` / `FAIL` / `BLOCKED` / `NOT_RUN` |
| 근거 유효성 | `current` / `stale` |

`NOT_RUN`은 미실행, `BLOCKED`는 실행 불가, `FAIL`은 실행했으나 기준 미충족, `PASS`는 지정 범위의 실제 기준 충족이다. 정적 package 검사·문구·파일 존재만으로 호스트 통합 행동이나 공개 배포를 `PASS`로 만들지 않는다. 대상·환경·요구가 바뀌면 영향 근거는 `stale`로 보존하고 재검증한다.

프로필의 선택 필드 `verification_policy_version`이 정수 `1`이면 각 check에 다음 분류와 실행 경계를 기록한다. 필드가 없으면 기존 `check_scope`의 키·검사·상태 전이를 유지하며 새 필드를 요구하지 않는다.

```text
verification.category: code_conditions | real_components | exploit_reproduction
verification.rationale: 비어 있지 않은 근거
verification.residual_uncertainty: 비어 있지 않은 잔여 불확실성
execution_boundary.status: recorded | needs_confirmation | blocked
execution_boundary.authority_basis / scope: 비어 있지 않은 근거와 범위
```

`code_conditions`는 정적 조건, `real_components`는 격리된 실제 구성요소 기능 시험, `exploit_reproduction`은 실제 침입·악용 재현이 필수인 예외다. 예외에는 `real_components` 방어 검증만으로 부족한 이유, 구체 범위, 사전 사용자 질문·동의, 플랫폼 허용을 기록한다. 기본 계획에 재현 check를 자동 생성하지 않는다.

`recorded`와 `user_confirmed`는 호스트가 근거를 기록한 사실일 뿐 실제 권한 인증·플랫폼 승인·재현 허용이 아니다. `needs_confirmation` 또는 `blocked`인 check는 `PASS`를 제출할 수 없고 required check라면 `TASK_DONE`과 `RELEASE_READY`를 막는다. 이 실행 경계 상태만으로 `PLAN_READY`를 막지는 않는다. 기존 FAIL·BLOCKED·NOT_RUN, 검토 request_changes·blocked와 finding은 append-only로 보존하며, 실패를 감추기 위해 category·scope를 바꾸지 않는다.

작업 종료와 릴리즈 후보 확정 시 정리 여부를 확인한다. 승인 근거와 실패·재현·최종 증거 및 참조 자료는 별도의 보존 변경 결정 전까지 유지한다. 삭제 후보는 해당 작업이 만든 재생성 가능한 임시물 또는 동일하고 참조되지 않는 중복으로 한정하고 종료 검토 전까지 보존한다. 이후 구체 목록과 허용 범위를 확인해 실행하며 기존 승인된 정리는 존중한다. 임의 TTL·자동 삭제·중복 백업을 강제하지 않는다.

## 릴리즈 기준

`TASK_DONE`은 적용되는 완료 기준의 충족 기록이며 `RELEASE_READY`는 별도 릴리즈 기준 충족 기록이다. 사용자·프로젝트의 필수 검토와 검증을 적용하고 실제 대상·근거를 확인한다. 릴리즈 판단은 배포 실행이나 외부 게시 권한이 아니다.
중요한 미해결 finding, 필수 검토 미완료, required 검증의 미확인·FAIL·BLOCKED·NOT_RUN이 남으면 `RELEASE_READY`로 기록할 수 없다. 예외가 필요하면 사용자에게 근거·잔여 위험·담당·만료일을 제시해 별도 승인받으며, 예외 승인으로 결과를 `PASS`로 바꾸지 않는다.

## 설치와 복구의 기록 경계

등록 위치는 [Codex 안내](../../../references/hosts/codex.md)를 따른다. 바탕 skill 하나만 등록한다. 마디 절차는 `skills/batang/components/madi/workflow.md`에 내부 문서로 보존한다. 재현 가능한 설치는 전체 checkout을 고정 revision으로 유지하고 `skills/batang`에 대한 단일 skill 등록을 만든다. 전체 checkout을 보존해야 내부 문서와 프로젝트 예시의 상대 참조가 유효하다.

전환 전 현재 Batang 및 Madi 등록의 정확한 경로와 link target을 관찰한다. 기존 Madi link가 이 설치의 이전 snapshot을 가리키는 예상 대상이며 소유가 확인된 경우에만 전환 계획에 따라 회수한다. 대상이 다르거나 소유가 불명확하면 멈추고 보고한다. 의도한 새 Batang 등록이 이미 있으면 중복 추가하지 않으며, 다른 checkout을 가리키는 기존 Batang 등록은 구체적인 변경안 없이 덮어쓰거나 삭제하지 않는다. 이전 snapshot과 기존 run은 그대로 둔다.

기존 개인 규약의 선별 분리는 명시적으로 승인된 이전 작업에서만 출처·소유·현재 hash·참조를 대조한 뒤 수행한다. 불명확하거나 예상과 다른 항목은 보존하고 계획을 조정한다. 일반 역할·모델·도구 설정과 다른 프로젝트의 정책은 자동 이전하거나 삭제하지 않는다. 스킬 호출마다 전역 파일을 설치·삭제하지 않는다.

등록 위치와 명령은 실제 호스트 안내에서 선택하고 충돌 없는 대상에만 적용한다.

등록 후 실제 link target과 checkout revision, root `SHA256SUMS`의 각 파일 hash 및 `SHA256SUMS` 자체의 hash를 확인한다. 기존 두 등록에서 새 단일 등록으로 이전하는 경우에는 새 Batang link를 먼저 검증한 뒤, 사전 관찰에서 이 설치의 소유로 확인된 예상 Madi link만 제거한다. 다른 link나 파일은 보존한다. 링크 대상의 변경·회수 순서가 실패하면 이번 작업에서 바꾼 link만 실제 target과 현재 상태를 재확인해 조건부 복구한다.

등록 명령은 대상 경로가 아직 없고 선택한 호스트 안내와 승인 범위가 허용할 때만 실행한다. 기존 등록이 다른 대상을 가리키거나 변경 범위가 불명확하면 중단한다. 실제 link 전환·예상 Madi link 회수·복구 성공은 해당 호스트에서 관찰해야 한다. 이 패키지는 installer, link 조작 코드, rollback 실행기를 제공하지 않는다.

제거·복구는 해당 설치 link 선택만 다룬다. immutable snapshot, vault, AGENTS 설정, backup, Graphify 결과, 기존 run은 제거하지 않는다. 기존 API 필수 project/run은 공개판으로 자동 전환하지 않는다.

## 개발 원본과 공개 package

개발 원본에는 제품 자료와 로컬 개발·검증 기록이 함께 있을 수 있다. 공개 package는 승인된 allowlist에 속한 제품 파일에서 새 staging 디렉터리로 산출한다. 로컬 run 결과, 프로젝트별 상태·finding, 개인 경로, 개발 일정은 공개 staging으로 복사하지 않는다. 상태값의 의미와 빈 재사용 양식은 제품 계약으로 유지할 수 있다.

1. 작업 범위와 allowlist를 승인 근거에 고정하고, 새 staging 디렉터리에 허용 파일만 복제한다. 원본 개발 파일은 유지한다.
2. 고정 전에 공개 릴리즈 정보를 개발 원본과 승인 기록에 대조해 갱신한다. 공개 버전, 사용자에게 보이는 변경 요약, 지원 환경, 외부 의존성의 버전·revision을 확인한다. 정보가 없거나 확인되지 않은 값을 공개 사실처럼 쓰지 않는다. 로컬 실행 결과와 게시 전 상태는 공개 설명에 넣지 않고 run 기록에 남긴다. 개발 원본의 revision/hash와 갱신할 공개 버전을 연결해 기록한다.
3. staging에서 package 파일 목록, 내부 참조와 공개 문구를 확인한다. 허용 파일별 SHA-256을 계산하고 `SHA256SUMS`, manifest, 배포 archive를 만든다. manifest와 archive hash로 공개 대상을 고정한다. 공개 version·변경 요약·지원 범위·의존성 고지와 이 연결 정보가 함께 고정됐는지 확인한다.
4. 선택하거나 필수로 요구된 검사와 검토는 해당 고정 bytes와 manifest hash를 대상으로 한다. 각 결과와 근거 및 실패 이력은 로컬 run 기록에 남긴다.
5. A/B 비교는 같은 승인 기준과 검증 범위로 수행한다. 배포 대상으로 선택할 후보는 마지막 배포 직전에 결정하며, 더 최신 후보가 모든 필수 게이트를 통과했는지 확인한다. `RELEASE_READY`는 고정 후보의 대상·hash, 승인 범위, 필수 검토·검증, 미해결 finding을 대조한 뒤 호스트가 기록한다.
6. hash 고정 후 파일이 달라지면 그 결과를 해당 고정본의 검증으로 사용하지 않는다. 새 staging 후보를 만들고 새 hash를 고정한 뒤 변경 영향이 있는 검증과 적용 규약이 요구하는 검토를 다시 수행한다. 이전 후보와 그 결과는 기존 로컬 기록에 보존한다.

공개 package에는 실제 run 기록이나 후보별 검증 결과를 넣지 않는다. 릴리즈 판단과 외부 게시·배포 권한은 별도이며 이 절차는 자동 게시나 `RELEASE_READY` 판정을 제공하지 않는다.
