# 마디

설계 책임 이름에서 `마디`는 바탕의 상위 개발·문서·도면 책임이며, 이 문서는 해당 작업 절차를 적습니다. 바탕 스킬은 관련 개발·문서·도면 요청에서만 이 절차를 읽고, 일반 지식 흐름에는 적용하지 않습니다. [보기](../supul/bogi/workflow.md)는 `수풀` 아래에서 요청된 설명·시각화를 맡고 Archify는 요청 때만 사용합니다. 두 절차의 참조 자체는 별도 에이전트 생성 요청이 아닙니다. 실제 실행과 권한은 현재 호스트와 프로젝트가 맡으며, 별도 실행 모듈·CLI·API·loader·provider·hook은 제공하지 않습니다.

## 시작 전 확인

1. 실제 적용되는 사용자·프로젝트 정책과 호스트 진입 계약의 필요한 조항을 확인하고 유효한 원문을 재사용한다. 현재 요청의 승인 범위, 자료 접근 권한, 변경 금지 영역, 기존 run을 확인한다.
2. 지식 자료가 필요한 작업에서는 프로젝트가 지정한 Obsidian vault와 활성 목록만 읽거나 쓴다. 독립 코드·문서 작업에 운영 vault를 선행 조건으로 삼지 않는다. vault 전체를 자동 탐색·편입하지 않는다. vault 또는 활성 목록이 없거나 충돌하면 필요한 이름·위치·포함 파일을 제시하고 명시 승인 전에는 만들거나 덮어쓰지 않는다.
3. 요청된 작업에 필요한 자료와 도구의 접근을 확인한다. Markdown 직접 조회에는 Graphify와 Archify가 필요하지 않다. 호스트는 Markdown을 직접 다루며 Obsidian 앱을 자동으로 열거나 등록하지 않는다. Graphify는 관계 작업과 승인된 갱신에 쓰고, Archify는 요청된 시각화에만 실행한다. 유효한 준비 근거의 재사용과 재확인은 [가닥](../gadak/workflow.md)을 따르며 실제 위치와 접근을 확인하고 자동 설치·경로 탐색·provider 대체는 하지 않는다.
4. 등록된 [바탕 스킬](../../SKILL.md)과 이 내부 절차의 동일 checkout 및 root `SHA256SUMS` 각 파일과 manifest 자체 hash에 대한 유효한 근거를 확인하고 bundle identity를 run에 기록한다. 유효 근거 재사용과 재확인은 [가닥](../gadak/workflow.md)의 조건을 따른다. profile hash는 실제 저장한 profile bytes에서 계산해 run 기록에만 둔다. release의 `candidate-manifest.json`과 archive hash는 별도 후보 근거로 보존한다. 불일치하면 개발 절차의 결합만 중단하고 바탕 지식 기능까지 차단하지 않는다.

## 계획과 기록

목표·범위·제약·기존 결정을 정리하고, 사용자 결정·위임된 세부결정·가정·미정을 구분한다. 관련 형식은 선택 가능한 참고 자료다. 기존 프로젝트의 계획·기록 방식을 존중한다.

적용되는 호스트가 재위임을 허용한 경우 배정된 planner는 [업무배정](../../references/delegation.md)에 따라 작업자와 독립 검토를 직접 관리하고 결과를 취합한다. 실제 파일 편집은 지정된 작업자가 맡고, 최상위 부모는 승인 범위와 최종 종료를 판단한다. 도면이 필요한 개발·문서 작업은 보기를 참조하되 적용되는 검토를 유지한다.

- 결정: [결정 기록](assets/decision-record.md)
- 프로젝트 조정값: [프로젝트 프로필](assets/project-profile.md)
- 계획: [상세 실행 계획](assets/execution-plan.md)
- 작업별 근거: [실행 기록](assets/run-record.md)

표현은 [공통 표현 지침](references/clear-language.md)을 따른다. 문서 작업이면 [문서 작업 지침](references/document-workflow.md), 도면 작업이면 [도면 작업 지침](references/diagram-workflow.md)을 추가로 읽는다. 사용자 검토·승인이 필요한 경우 [사용자 검토 표시 지침](references/user-review-presentation.md)을 따른다. 역할·상태·검증·기록 경계는 [실행 계약](references/workflow-contract.md)의 해당 조항을 따른다. 설치·복구·릴리즈 상세는 해당 작업에 필요할 때 확인한다.

## 중요한 경계

- `PLAN_READY`, `TASK_DONE`, `RELEASE_READY`는 호스트가 실제 Markdown 근거와 프로젝트 계약을 읽어 내리는 기록 상태다. 이 패키지는 이 값을 자동으로 검사·제출·전환하지 않는다.
- `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`도 실제 관찰 범위의 기록이다. 파일 존재, 문구 일치, 설치 선택값, 합성 호출만으로 실제 호스트 동작이나 릴리즈 준비를 `PASS`로 바꾸지 않는다.
- 기존 API 기반 profile/run 또는 이전 snapshot은 보존한다. 공개판으로 자동 전환·이관·재작성하지 않으며, 기존 API가 필요한 run의 지침과 기록을 대체하지 않는다.
- 개발 원본에서 공개 package를 만들 때는 승인된 allowlist만 새 staging으로 추출하고 manifest·checksum hash를 고정한다. 공개 package와 로컬 실행 기록의 경계, 고정본 이후 검증 순서, 배포 직전 릴리즈 판단은 [공개 package와 릴리즈 계약](references/workflow-contract.md)을 따른다.
- 업무 배정은 [바탕 업무배정](../../references/delegation.md)을 따르고, 위임 주체·깊이·슬롯·허용 도구는 실제 적용되는 사용자·프로젝트·호스트 규약과 권한 한도를 따른다. 메인은 필요한 정책·범위를 전달하고 결과를 확인한다. 자식은 수신한 범위와 실제 재위임 규약을 따른다.
- 검토의 필요성·종류·순서·횟수와 릴리즈 조건은 적용 규약을 따른다. 필수 모델·검토를 수행하거나 확인하지 못하면 해당 단계는 `BLOCKED`다. 실제 독립 검토에는 대상과 독립성·호출 근거를 보존한다.
- 기존 정책·계획·기록 방식을 존중하며 프로필이나 모델 설정을 자동 생성하지 않는다. [설정 예시](../../../../examples/AGENTS.md)는 선택적 참고다.
- 바탕만 사용자 또는 프로젝트 skill로 등록한다. 이 내부 마디 절차는 같은 checkout에 보존하며 별도 skill로 등록하지 않는다.

## 설치·기존 run·새 run의 구분

설치된 link, 현재 세션이 읽은 파일, 새 run이 고정한 checkout은 서로 다를 수 있다. 기존 run은 시작 시 고정한 경로·지침·기록을 계속 사용하며, 진행 중 run의 실제 파일은 경로와 hash가 고정된 동안 수정하지 않는다. 새 후보는 별도 checkout 또는 고정 디렉터리에 준비해 이후 run에서 선택한다. 기존 설치·run·vault·Graphify 결과를 임의로 변경하거나 제거하지 않는다.

설치 또는 링크 전환의 실제 성공 여부는 격리된 실제 호스트 관찰로만 확인한다. 이 문서와 정적 검사는 package allowlist·참조·경계를 확인할 뿐, 단일 바탕 link 전환, 기존 마디 link 회수·복구 또는 vault 보존을 보증하지 않는다.

프로젝트의 필수 모델·모드와 검토 기준을 유지하고, 허용된 대체만 선택한다. 실제 배정·호출과 실패 근거는 기존 기록 방식에 보존한다.
